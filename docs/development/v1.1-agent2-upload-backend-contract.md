# V1.1 Agent 2 Upload Backend Contract

This is the frontend handoff for ScanStory V1.1 resumable uploads. It does
not replace `resumable-upload-api-contract.md`; it highlights the fields Agent
2 should bind to for slow/interrupted upload UX.

## Routes

- `POST /api/uploads/sessions`
- `POST /api/uploads/sessions/<id>/chunk`
- `GET /api/uploads/sessions/<id>`
- `POST /api/uploads/sessions/<id>/finalize`
- `POST /api/uploads/sessions/<id>/cancel`

All POST routes keep existing CSRF behavior. Chunks remain one sequential byte
stream: marker image bytes first, then video bytes. Use `X-Chunk-Offset` for
every chunk request.

## Status Recovery

After any network error, refresh, `OFFSET_MISMATCH`, or lost finalize response,
call `GET /api/uploads/sessions/<id>` and trust the returned session object:

- `uploaded_bytes`
- `remaining_bytes`
- `progress_percent`
- `can_upload_chunks`
- `can_finalize`
- `can_retry_finalize`
- `can_cancel`
- `is_terminal`
- `project_id`
- `pair_id`
- `pair`
- `processing_job`

Do not restart from byte zero unless the old session is terminal and not
`completed`.

## Finalize Recovery

- `completed`: exactly one Project exists; redirect using `project_id`.
- `assembled`: Project/Pair and quota already exist, but enqueue failed. Retry
  `finalize`; do not upload bytes again and do not create a new session.
- `active` with `can_finalize=true`: upload bytes are complete; call
  `finalize`.
- `active` with `can_upload_chunks=true`: resume from `uploaded_bytes`.

## Completion

Finalize success means Project/Pair were created and processing was queued.
Processing completion remains asynchronous. Use `processing_job.status` and
`pair.processing_status` for visible queued/processing/failed/ready messaging.

No response exposes local filesystem paths, uploaded content, secrets, or raw
tracebacks.
